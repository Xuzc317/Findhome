## 一、先说结论：这个项目的思路其实很简单

很多人找房时的真实想法是这样的：

> 我在**这几个地铁站**附近找房，预算 **1200–2500**，要**单间或一房一厅**，
> **步行不超过 20 分钟**，最好**有电梯、别太旧**。

但你去任何一个租房平台，它的筛选条件都是：城市 → 行政区 → 价格 → 户型。

**没有平台支持"按地铁站 + 步行时间"反查。**

于是整个项目的核心就三步：

| 步骤 | 做什么 | 难点 |
|---|---|---|
| ① 定位置 | 先选几个地铁站，而不是选行政区 | 几乎没有 |
| ② 去采集 | 到闲鱼/小红书/豆瓣搜这些站附近的房源 | **平台风控** |
| ③ 算距离再筛 | 用高德算每条房源到地铁站的真实步行时间，超时的删掉 | 几乎没有 |

**剩下的全是在这三步上的打磨**：识别转租、标注疑似中介、保存收藏备注。

之所以说它容易实现，是因为**每一步都有现成的 API 或开源代码**：

- **采集**：豆瓣用 `requests + BeautifulSoup` 就能直接拿
- **地铁数据**：中文维基有站序，Wikidata 有坐标
- **步行距离**：高德 Web 服务 API 直接返回路径距离和耗时
- **界面**：Ant Design 组件库，粘过来就能用

真正花时间的**不是"写代码"，而是踩数据与平台风控的坑**（见第七节）。

## 三、几个我觉得有意思的设计

### 1. 真实步行距离，而不是直线距离

这个是整个项目最有价值的地方。

直线距离 300 米的房子，实际走路可能要 800 米、绕 10 分钟——
因为中间隔着快速路或工地。我实测过一套：

| 房源 | 直线距离 | **真实步行** |
|---|---|---|
| 车公庙附近某小区 | 282 米 | **821 米 / 11 分钟** |

差了近 3 倍。所以项目里**直线距离只用来做 3 公里预筛**（零成本），
真正判断"能不能接受"的是高德算出来的步行路径。

### 2. 转租识别

找过房的人都知道，中介发的图和价经常不实。

但**转租贴不一样**——转租是原租客因为换工作、要离开深圳等原因转让合同，
图片和价格通常是真的，而且中介基本不做这类生意。

所以项目会自动把房源分成三类：`转租` / `直接房东` / `普通`，
可以只看转租。

实测效果差别很明显：同样的搜索词，
小红书搜「租房」单次只能出 2–5 条房源，搜「**转租**」能出 12–16 条。

### 3. 疑似中介标注

这个功能是被**用户的真实经历**逼出来的：

> 我在采集结果里挑了 3 套满意的，联系中介后被告知——**图片全是宣传图**。

排查后发现：那 3 套**全部来自同一个账号**，而这个账号在租房源 **98 套**。

于是从图片 URL 里提取发布者 ID，统计每个账号的在租数量：

| 发布者类型 | 账号数 | 覆盖房源 |
|---|---|---|
| 只挂 1 套 | 507 个 | 507 条 |
| **挂 ≥5 套** | **9 个** | **259 条（26%）** |

一个账号挂几十上百套的，基本就是中介/机构。现在卡片上会直接标注，
并且可以一键"只看个人房东"。

**注意**：这个功能**不能判断图片真伪**，只能标注发布者身份供你参考。
所以项目里也明确写了提示：

> 房源图由发布者上传，可能是宣传图，不等于实际房间。建议先要实拍视频。

### 4. 不伪造数据

这条是我在开发中反复坚持的原则：

- **只写"某站附近"、没有小区名的房源，不会拿站点坐标当房源坐标**
  （那会让距离算成 0 米，看着完美实际是假的），而是单独列为"位置待确认"
- **电梯状态区分**「原文明确写了」和「按楼层推断」，不把推断当事实
- **平台不给发布时间的，就留空**，不拿采集时间冒充发布时间
- **价格解析不出来就留空**，不猜

## 四、技术选型（都很常规）

| 层级 | 选型 | 说明 |
|---|---|---|
| 前端 | React 18 + TypeScript + Vite 5 + Ant Design 5 | 5 个页面，无账号体系 |
| 后端 | FastAPI + SQLAlchemy 2 | 标准 REST |
| 数据库 | SQLite | 单文件零配置，本地用足够 |
| 采集 | httpx + BeautifulSoup / Playwright | Adapter 模式，各平台独立 |
| 地理 | 高德 Web 服务 API | 地理编码 / POI / 步行路径 |
| 大模型 | DeepSeek / 豆包 | 从文字图片推断房源位置 |

**没有黑魔法**，全都是主流且文档齐全的技术栈。

### 一个值得说的取舍：采集分两类

- **豆瓣**：普通 HTTP 请求就能拿
- **闲鱼 / 小红书**：搜索接口要求页面 JS 生成的签名参数

对于后者，我**没有去做签名逆向**（那是绕过访问控制），
而是用 Playwright 打开真实浏览器、只读页面渲染出来的结果——
**这跟手工浏览没有任何区别**。

## 五、AI 是怎么参与这个项目的

这个项目由人和 AI 共同完成，分工很明确：

| 环节 | 承担者 |
|---|---|
| 任务规划、需求拆解、**使用界限声明**、验收标准 | WorkBuddy AI、ChatGPT |
| 代码实现、测试编写、排查、提交推送 | DeepSeek Harness |

几点真实体会：

**① AI 最擅长的不是写代码，而是"把模糊需求变成明确任务"。**
比如我说"要能按地铁站筛房"，它会反问：直线距离还是步行距离？
只写站名的房源怎么处理？同时选多个站怎么算？

**② AI 会写错，而且错得很隐蔽。**
这一点很重要，见下一节。

**③ 校验比生成更重要。**
这个项目里我抓出的每一个真 bug，都不是 AI 主动告诉我的，
而是**跑测试、对数据、验渲染**发现的。

## 六、部署（就几条命令）

```bash
git clone https://github.com/Xuzc317/Findhome.git
cd Findhome

# 后端依赖
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 浏览器内核（闲鱼/小红书采集必需）
python -m playwright install chromium

# 前端
cd frontend && npm install && npm run build && cd ..

# 配置（至少填高德 Web 服务 Key）
cp .env.example .env

# 启动（必须在项目根目录）
uvicorn backend.main:app --host 0.0.0.0 --port 8000
```

打开 <http://localhost:8000> 就是上面演示的界面。

高德 Key 申请：<https://console.amap.com/dev/key/app>
（注意要申请「**Web服务**」类型的 Key，不是「Web端(JS API)」，
两类不能混用，填错会报 `10009`）

## 七、踩过的坑（这部分最值得看）

这一节的内容全部来自真实的提交记录。**AI 写的代码出错时，往往不是报错，
而是"看起来正常但数据是假的"**——这种最难发现。

### 坑 1：755 条房源抓成了同一张图

给房源加图片后，我抽查发现一个问题：

> **755 / 982 条房源共用同一张图**

排查后确认：那不是房源图，而是闲鱼的**懒加载占位图**——
抓取时图片还没加载完，`img.src` 还停在占位资源上。

**这比没有图更糟**：用户会以为所有房源长得一样。

修复：抓取前先滚动页面触发懒加载，再做**占位图检测**
（同一页里出现 ≥3 次的图片一定是站点占位图，一律丢弃）。

修复后实测：**30 条全部有图，且 30 张互不相同**。

### 坑 2：「无电梯」被判成「有电梯」

电梯识别最初的正则里，肯定式是这样写的：`电梯房|有电梯|带电梯`。

问题是 `无电梯` 里**也包含"电梯"两个字**。如果否定式没先匹配，
"无电梯"会被判成"有电梯"——**这是最要命的一类错误**，
因为用户会白跑一趟。

修复：**否定式必须优先匹配**。这是个经典的正则顺序问题。

### 坑 3：把 1900–2100 元当成年份排除了

价格解析最初为了避免把"2024年"当成租金，写了一行：

```python
if 1900 <= price <= 2100:   # 认为是年份
    continue
```

看起来很合理——但这恰是**最常见的租金区间**！

结果 `一房一厅2000`、`大单间1950` 这类房源价格全被丢掉了。

修复：**看上下文而不是看数值**——只有数字后面紧跟"年"字才当成年份。

### 坑 4：坐标系混用，距离偏了几百米

高德用的是 **GCJ-02** 坐标系，而 Wikidata、维基百科给的是 **WGS-84**。

深圳地区两者相差约 **600 米**。如果不做转换直接混用，
算出来的步行距离会系统性偏移几百米。

修复：所有入库坐标统一转成 GCJ-02，并记录坐标来源。

### 坑 5：测试期望值算错了

有一次 CI 报红，我一开始以为是代码 bug，查了才发现是**测试自己写错了**：

```python
# 测试只在"标题"里数有多少条含"中介"
hit = sum(1 for h in items if "中介" in h["title"])
# 但过滤逻辑是匹配"所有文本列"（标题+正文+…）
```

结果：期望排除 27 条，实际排除了 279 条。

**修正后的做法**：不再用"字段覆盖范围"这种实现细节推算期望值，
而是检验**行为契约**——

- 排除后不能清零（这才是当初那个 NULL 空值 bug 的回归点）
- 排除后总数只能减少不能增加
- 排除一个不存在的词，总数应完全不变

### 坑 6：只推了标签，没推主分支

这个不是代码 bug，是操作失误，但后果很隐蔽：

改完历史后我创建了 `v1.0.0` 标签并推送，**但忘了推 `main` 分支**。
结果标签指向了一个**不在主线上的孤立提交**——
别人点标签下载到的内容，跟仓库首页看到的不是一回事。

这个错误在推送时**没有任何报错**。是我后来做一致性校验时发现的
（用 `git merge-base --is-ancestor` 检查标签是否在主线）。

### 小结

上面 6 个坑里，**只有坑 5 是"报错"暴露的，其余 5 个都是主动校验才发现的**。

所以我的体会是：**AI 写代码的效率确实高，但校验环节一点都不能省。**
尤其是"看起来有数据、其实是假数据"这种情况。

## 九、边界声明（重要）

这个项目有几条**不会突破的底线**：

- ❌ 不绕过验证码、登录或访问控制
- ❌ 不逆向平台签名算法
- ❌ 不使用他人账号
- ✅ 只使用**你本人浏览器**的登录态（不索取密码）
- ✅ 密钥与 Cookie 只存本地 `.env`，不上传任何服务器
- ✅ 所有数据只落在本地 SQLite

**也请使用者注意**：

- 采集请控制频率、遵守各平台服务条款
- 本项目仅供**个人学习与自查**使用，不要用于批量倒卖或商业分发

一个真实的教训：开发过程中我的脚本就因为**请求过于频繁被平台检测**过。
所以项目最终改成了**按需采集**——你点"开始"它才去采，采完就停，
而不是 24 小时不间断爬虫。
